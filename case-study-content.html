Problem Statement

Discovery is how users find what they didn’t know they wanted. And yes, it’s the most politely aggressive part of your product.

A content discovery system powers personalized homepages, search results, recommendation carousels, and trending feeds. At scale, it becomes a distributed system combining metadata, retrieval, ranking, personalization, caching, and real-time signals.

Requirements

Functional

  • Personalized recommendations for homepage & carousels
  • Keyword-based search discovery
  • Trending / popular content surfacing
  • Near real-time updates to rankings
  • Multi-device support (web, mobile, TV)

Non-functional

  • Low latency: < 200ms P95 for discovery queries
  • High availability: 99.9%+ with graceful degradation
  • Horizontal scalability to millions of users
  • High read throughput (often 100:1 reads:writes)
  • Fault tolerance & observability
Design Constraint

Latency budgets should be explicit: the orchestrator enforces timeouts and fallbacks so the UI never “hangs” waiting for personalization.

High-level Architecture

We’ll use a discovery orchestrator that fans out to recommendation, trending, search, and metadata services, then returns a ranked, hydrated response.

Diagram A: High-level Architecture

Client → Gateway → Orchestrator → (Rec/Search/Trending/Metadata) → Rank → Cache

The Discovery Orchestrator enforces a latency budget: it fans out in parallel, aggregates results, applies business rules, hydrates metadata, and returns a ranked response. Caching lives at multiple layers.

End-to-end Request Flow

When a user opens the homepage, the system typically:

  1. Client → API Gateway → Discovery Service
  2. Discovery fans out to Recommendation, Trending, Search, Metadata
  3. Rank / re-rank candidates and apply business constraints
  4. Cache final ranked list and respond
Key Pattern

The orchestrator prevents any single downstream dependency from becoming a “single point of user frustration.”

Core Services

Discovery Orchestrator

  • Parallel fan-out to upstream sources
  • Enforces timeouts & fallbacks
  • Applies business logic & experimentation
  • Response shaping per device/UI

Recommendation Pipeline

  • Candidate generation (fast, broad)
  • Filtering (policy, availability, diversity)
  • Ranking (ML or heuristics)
  • Re-ranking (context: session, device, time)

Diagram B: Recommendation Stages

Generate → Filter → Rank → Re-rank

Candidate generation must be extremely fast; ranking provides precision. Many systems use a hybrid: precomputed candidates + online re-ranking for context.

Search integration

  • Full-text index (OpenSearch/Elasticsearch)
  • Semantic/vector search for intent
  • Autocomplete + query suggestions
  • Unified metadata consistency with recs

Metadata hydration

  • Titles, tags, images, availability
  • Region/device eligibility rules
  • De-normalized read models
  • Cache-friendly payload shaping

Metadata & Indexing Pipeline

Discovery quality is often gated less by your ranking model and more by whether your metadata is correct, complete, and fresh.

Diagram C: Metadata Ingestion & Indexing

Ingest → Store → Index → Feature store

Split paths: indexing updates search retrieval, while features power personalization and ranking. Use batch for depth and streaming for freshness.

Reality Check

If your metadata pipeline is wrong, your “perfect model” will confidently recommend broken links. Machines can be very persuasive liars.

Scaling & Caching

Discovery is usually read-heavy. Optimize for reads with multi-layer caching and precomputed candidates.

Cache layer Purpose Typical TTL
CDN Static / anonymous discovery, shell responses, common assets Seconds → minutes
Edge cache Geo-aware personalization for “lightly personalized” segments Seconds
Redis Hot per-user recommendation lists, trending pools 10s → few minutes
Service cache Ranked results, metadata hydration, expensive joins Short TTL + invalidation
Pro Tip

Cache the final ranked list (when safe), not just raw candidates. That avoids re-running expensive ranking on every request.

Real-time Personalization

For sub-minute personalization, stream user events into an online feature store consumed by ranking services.

Diagram D: Streaming Signals → Feature Store → Online Ranking

Events • Kafka/Kinesis • Flink/Spark • Feature store

Streaming keeps personalization fresh while keeping request latency low: compute features continuously, then score quickly online.

Latency Optimization

Tactics

  • Parallel fan-out calls (async)
  • Precompute candidate pools
  • Cache ranked responses
  • Short-circuit slow dependencies
  • Edge caching for anonymous traffic

Graceful Degradation

  • If personalization times out → fallback to trending
  • If metadata hydration fails → return minimal cards
  • If search index lags → serve last known good
  • Load shedding during spikes
Latency Budget Rule

The orchestrator should treat downstream services like a buffet: you take what’s ready before the kitchen closes.

Tradeoffs

Decision Option A Option B Typical Choice
Consistency vs Freshness Strong consistency (slower) Eventual consistency (faster) Eventual consistency for feeds
Precompute vs Real-time Rank Precompute (cheap, fast) Real-time (more relevant, costly) Hybrid: precompute + re-rank
Unified vs Separate Indexes Unified metadata/index Separate per feature team Unified for consistency
Fan-out Orchestration Central orchestrator Client-side aggregation Central orchestrator

Failure Scenarios & Resilience

Common Failure Modes

  • Recommendation service timeout
  • Cache-miss stampede
  • Search index lag / partial outage
  • Feature store skew / stale features
  • Model regression (quality drop)

Mitigations

  • Circuit breakers + per-call timeouts
  • Request coalescing + jittered TTLs
  • Fallback pools: trending / editorial
  • Multi-region failover paths
  • Quality monitoring + rapid rollback
Operational Truth

Resilience is less about “never failing” and more about “failing in ways the user barely notices.”
