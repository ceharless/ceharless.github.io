Case Study: Modernizing Search

A pragmatic, incremental plan to transform “Search is scary” into “Search is boring” — by stabilizing reliability, speeding delivery, and extracting a Search service from a legacy monolith.

Search is one of the most visible user experiences — and one of the easiest ways to accidentally melt your backend. Today, Search lives inside a legacy Java monolith, shares a database with everything else, and is tightly coupled to product releases. The result: slow iteration and frequent “why is Search down again?” incidents.

TL;DR Pitch

Improve observability + safe releases first, then extract Search using a strangler approach. Deliver measurable wins every 4–6 weeks without betting the business on a rewrite.

Problem Statement

What Users Experience

  • Slow or inconsistent results during peak usage
  • Irrelevant ranking (poor discovery → lower engagement)
  • Periodic outages that affect core flows

What Engineering Experiences

  • Search changes require full monolith releases
  • Hard-to-debug failures (limited observability)
  • Index rebuilds are manual + risky

Context & Constraints

Assumed Environment

  • Java monolith serving web + mobile APIs
  • Relational DB shared across domains
  • Search relies on DB queries + ad-hoc caching
  • Traffic spikes (events, promos, seasonality)

Constraints

  • No “pause product for 6 months” rewrite
  • Small-ish team (5–8 engineers) initially
  • Need measurable improvements quickly
  • Reliability is a feature (even if it’s not on the roadmap)
Principle: Make the riskiest thing smaller

Instead of one giant migration, we shrink risk by improving visibility + release safety first, then extracting Search incrementally using a strangler pattern. Every phase ships value.

Symptoms & Root Causes

Symptoms

  • Incidents: query storms, DB contention, cache stampedes
  • Slow delivery: Search improvements wait on monolith release trains
  • Debug pain: “What changed?” takes too long to answer

Root Causes

Tight Coupling

Search code, schema, and release cadence are entangled with unrelated product areas. A small ranking tweak becomes a full-system gamble.

Weak Guardrails

Limited timeouts, missing circuit breakers, and insufficient rate limiting allow one bad query to become everyone’s bad day.

Poor Observability

If you can’t see it, you can’t fix it. Lack of tracing + correlation IDs makes root cause analysis slow.

Unclear Ownership

“Search is everyone’s responsibility” becomes “Search is nobody’s responsibility.” Incidents repeat.

Goals & Success Metrics

This plan is designed to show how I translate an ambiguous “Search is bad” complaint into measurable outcomes.

Reliability

  • Cut Search-related incidents by 50%
  • Reduce MTTR from ~60 minutes to <15 minutes
  • Establish SLOs and an error budget to guide tradeoffs

Performance & Delivery

  • Improve Search p95 latency: ~900ms → <250ms
  • Increase deployment frequency: weekly → daily
  • Reduce change failure rate with canaries + fast rollback

Proposed Plan

The plan has three phases. Each phase reduces risk and improves outcomes without blocking product delivery.

1

Phase 1 (Weeks 1–4): Stabilize Search

Add observability, guardrails, and incident hygiene so we can measure, debug, and recover quickly.

  • Define Search SLOs (availability + latency) and baseline current metrics
  • Add correlation IDs + tracing across request → search execution → datastore
  • Implement rate limiting, timeouts, circuit breakers for known hotspots
  • Create an incident playbook + postmortem workflow (action items must have owners/dates)
Definition of Done

Dashboards answer: “Is Search healthy?”, “What changed?”, and “Where is time spent?” On-call can roll back or mitigate within minutes.

2

Phase 2 (Weeks 3–8): Ship Safely and Frequently

Reduce blast radius with progressive delivery so Search changes don’t require bravery medals.

  • CI/CD improvements: parallel tests, quarantine flaky tests, faster build pipeline
  • Introduce feature flags for ranking/experiments
  • Canary releases for monolith Search changes + automated rollback triggers
  • Create a Search release checklist that becomes automation over time
Why This Matters for Search

Search changes can be high variance (query patterns, index shifts, ranking tweaks). Canary + rollback turns unknowns into controlled experiments.

3

Phase 3 (Weeks 6–20): Extract Search into Stable Service

Create a dedicated Search service behind a stable API contract, gradually routing traffic away from the monolith.

  • Define Search API contract (query, filters, pagination, facets, ranking params)
  • Stand up Search service (stateless) and Search index (e.g., OpenSearch/Elasticsearch or managed equivalent)
  • Build an indexing pipeline: source-of-truth events → indexing → validation
  • Route traffic gradually: 1% → 5% → 25% → 100% with canaries and rollback
Indexing Strategy

Begin being pragmatic at first and then cleanup later. Start with a nightly backfill + incremental updates from change events (CDC or app events). Add idempotency + replay to handle failures. Later, move toward stronger domain boundaries and ownership.

Tradeoffs

Rewrite vs Incremental Extraction

A full rewrite is tempting and often catastrophic. Incremental extraction delivers wins continuously and avoids a “big bang” cutover.

Shared DB vs Database Per Service

For Search, the index is the serving store; the DB remains source of truth. Early on, we can read from shared DB for indexing, then evolve toward clearer data ownership.

Relevance Quality vs Platform Reliability

Ranking experiments are valuable, but the system must be stable first. We sequence reliability/observability before aggressive relevance experimentation.

Latency vs Cost

Search infrastructure can get expensive if left unchecked. Set budgets and monitor cost-per-query, then tune index/shards/caches based on measured usage.

Risks & Mitigations

Risk: stale or inconsistent results

  • Mitigation: index update SLAs + replayable event stream
  • Mitigation: validation jobs (sample compare monolith vs service results)

Risk: traffic spikes overwhelm the index

  • Mitigation: rate limits, request shaping, caching hot queries
  • Mitigation: autoscaling + load tests using realistic query distributions

Risk: scope creep

  • Mitigation: enforce API boundaries + phased roadmap
  • Mitigation: define “not now” list (synonyms, personalization, etc.)

Risk: organizational issues and unclear ownership

  • Mitigation: explicit Search ownership + on-call rotation
  • Mitigation: operational readiness checklist before traffic ramp

Team & Operating Model

Search succeeds when it’s treated as a product and a platform and here is the lightweight operating model to establish.

Ownership

  • One team owns Search service + indexing pipeline + dashboards
  • Clear on-call rotation and escalation
  • Partner team owns source-of-truth data quality

Cadence

  • Weekly reliability review (top incidents, trends, action items)
  • Monthly performance/cost review (cost-per-query, capacity planning)
  • Experiment review for ranking changes (guardrails + metrics)
Metrics To Track

Deployment frequency, lead time for changes, change failure rate, MTTR, p95 latency, error rate, query volume, cost-per-query, index freshness lag.

First 30/60/90 Days

30

Days 1–30: Baseline + Guardrails

Instrument Search, define SLOs, stabilize incidents, and make “what happened?” answerable quickly.

  • Dashboards + alerts for latency/error/saturation
  • Top 3 failure modes mitigated (timeouts, rate limits, cache stampede protection)
  • Incident playbook + postmortem discipline
60

Days 31–60: Safer Releases + Contract Design

Improve CI/CD, introduce canaries/flags, and finalize the Search API contract and indexing approach.

  • Canary + rollback in place for Search changes
  • Search API contract reviewed with consumers
  • Index schema + pipeline design ready
90

Days 61–90: First Traffic on New Search Service

Deploy Search service + index, run shadow traffic, then start controlled ramp with guardrails.

  • Shadow mode comparisons (service vs monolith)
  • 1% traffic ramp with automated rollback triggers
  • Post-launch learnings → next extraction milestones

Artifacts

Search Service Level Objective

Service: Search API
SLOs:
  Availability: 99.9% (monthly)
  Latency: p95 < 250ms (monthly, excluding bots)

Error budget policy:
  - If error budget burn > 2x for 2 days → pause non-critical launches, focus on reliability
  - Canary required for ranking/index changes

Release Ramp Plan (Progressive Delivery)

Traffic ramp:
  0%  → shadow mode (compare results + latency)
  1%  → canary (alerts: error rate, p95, index freshness lag)
  5%  → validate peak window
  25% → validate scale + cost-per-query
  100%→ deprecate monolith search path (keep fallback temporarily)

Rollback triggers:
  - Error rate +X% over baseline for 5 min
  - p95 latency > baseline +Y% for 10 min
  - Index freshness lag > threshold
